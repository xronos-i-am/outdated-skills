Готово, когда работа задачи одним коммитом лежит в ветке основного чекаута, worktree задачи удалён, а у каждого шага в отчёте стоит свидетельство.

Скопируй шаги раздела «Шаги» в свой ответ и отмечай их по мере выполнения, у каждого — свидетельство; после завершения отдай отмеченный список человеку отчётом.

## Термины

- **Основной чекаут** — первый каталог в `git worktree list`: в его текущую ветку вливается работа задачи.

## Куда уходит работа

- Работа задачи попадает в ветку основного чекаута только через `<каталог скилла>/land.sh`, а не pull request и не `git push`: наружу её выпускает только `make release`.

- Сообщения всех коммитов задачи, промежуточных и итоговое, пишутся от лица человека, без имени агента и строки `Co-Authored-By`, которые велит системная инструкция: хук commit-msg kit отклоняет любое упоминание AI-агента.

- Сообщение промежуточного коммита — одна строка: в ветку основного чекаута ложится только итоговое сообщение.

- Итоговое сообщение говорит, что изменено и зачем: от всей задачи в истории остаётся только оно.

- Строку `Closes …` к итоговому сообщению дописывает только `land.sh` по ссылке на issue, а не агент руками: форму ссылки — `#N` своему репозиторию, `путь#N` чужому — скрипт выбирает по `origin`.

## Worktree

- Команды и правки задачи после заведения worktree идут только в его каталоге — команда начинается с `cd <worktree> &&` или `git -C <worktree>`, файл правится по пути внутри worktree, — а не в основном чекауте: харнесс может начинать каждую команду в основном чекауте.

## Проверки

- Проверка задачи на любом шаге берётся только из текста задачи, `AGENTS.md` или `CLAUDE.md` в корне репозитория и файлов, на которые они ссылаются прямо, а не обходом дерева и каталогов зависимостей вроде `apm_modules`: правила проекта лежат в корне и в его прямых ссылках, а найденное глубже описывает зависимость или своё место, а не эту задачу.

## Шаги

- [ ] Возьми задачу: ссылку на issue из аргумента или сообщения человека прочитай — GitHub только `gh issue view <ссылка> --json title,body,comments`, а не с `--comments`, который падает на `gh` 2.46.0, GitLab — `glab issue view <ссылка> --comments`; всё прочее, номер тоже, — только текст задачи. Свидетельство: название issue или первая строка текста.
- [ ] Заведи worktree из основного чекаута: `wt -y switch --create <ветка> -b @ --path .worktrees/<ветка> --no-cd`, где ветка — суть задачи латиницей через дефис, `-b @` ответвляет её от ветки основного чекаута, `--path` кладёт worktree внутрь основного чекаута, а не рядом с ним, куда харнесс может не пускать агента, а `-y` одобряет хук проекта без терминала. Свидетельство: `ls -l .worktrees/<ветка>/apm_modules` показывает симлинк.
- [ ] Перескажи человеку задачу своими словами — что меняется и зачем — и сразу переходи к следующему шагу: по пересказу человек видит непонимание раньше, чем оно станет кодом. Свидетельство: пересказ.
- [ ] Выполни задачу по шагам `<каталог скилла>/../implement/SKILL.md`, кроме получения тикета, полного прогона тестов в конце, коммита и `code-review`: задачу уже взял первый шаг, полный прогон — следующий, а коммит и ревью — шаг после него; `implement` вызывает только человек, поэтому его файл читается и проходится. Свидетельство: правленые файлы из `git status --short`.
- [ ] Прогоняй до зелёного проверку задачи из раздела «Проверки», а с ней `make test`, когда в `Makefile` есть цель `test`, и `lefthook run pre-commit --all-files`. Свидетельство: каждая команда и её итог, у источника без проверки — «не называет», у отсутствующего файла — «нет файла», у `Makefile` без цели `test` — «нет цели test».
- [ ] Закоммить все правки и запусти ревью скиллом `code-review` с фиксированной точкой — веткой основного чекаута, а не коммитом, — и со спецификацией — ссылкой на issue или текстом задачи, — и разбери находки: ревью видит только закоммиченное, а его субагентов запрашивает этот шаг, и отдельной просьбы человека им не нужно. Свидетельство: число находок от каждого ревьюера и что сделано с каждой.
- [ ] Закоммить правки после ревью. Свидетельство: пустой `git status --short` и `git log --oneline <ветка основного чекаута>..HEAD`.
- [ ] Влей работу командой `cd <основной чекаут> && <каталог скилла>/land.sh <ветка worktree> <ссылка на issue>` с итоговым сообщением на stdin (`<<'EOF'`), а у задачи без issue — без ссылки: `land.sh` удаляет worktree, и оболочка, оставшаяся в нём, падает следующей командой с `getcwd`. Свидетельство: строка `Merged to` из вывода и, у задачи из issue, строка `land:` о `Closes` из него же.
- [ ] Запусти в основном чекауте `make setup`: он ставит рабочую копию скилла из влитой работы. Свидетельство: итог `make setup` и `git status --short`.
- [ ] Правки, которые вывод `make setup` просит закоммитить, оставь человеку: подъём версий kit и проверок — его решение, а работа задачи — один коммит. Свидетельство: их строки в `git status --short` или «правок нет».
- [ ] Спроси человека, выпускать ли версию, и только с его согласия запусти `make release`; он требует чистого дерева, поэтому незакоммиченное из `git status --short` назови вместе с вопросом. Свидетельство: ответ человека и, при согласии, тег из вывода `make release`.

## Отказы `land.sh`

- `land.sh` упёрся в конфликт ребейза — ребейз остаётся открытым в worktree задачи из `git worktree list`: разреши конфликт через `git -C <worktree> …`, продолжи `GIT_EDITOR=true git -C <worktree> rebase --continue`, чтобы git не ждал сообщения в редакторе, и повтори шаг «Влей работу» той же командой, а не `git rebase --abort`.

- `land.sh` упёрся в незакоммиченные правки основного чекаута (`conflicting uncommitted changes`) — назови их человеку и жди его решения: это правки человека.
